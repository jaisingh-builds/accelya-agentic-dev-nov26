# M2 cancellation refund: three architecture options (standard queue, no ordering)

Region us-east-1. Volume 2,000 cancellations/day (about 60k a month), peaks of 50/minute.
Ordering: **No.** Each event is decided independently from its own fields (`refund_rules.json` has no rule that reads other events or mentions PNR). Duplicates must be safe: idempotent on `event_id`.
Producer: the existing passenger-facing API (HTTPS), which returns 202 and publishes the event.
Non-goals: no Kinesis or MSK, no EC2, no logging of passenger names, emails or fare amounts, no Bedrock or ML in the decision path, no multi-region.
Hop answers follow `docs/service-boundary-6q.md`.

**Open questions for the business owner:**
1. Is there any case where event order changes the result (for example cancel, reinstate, cancel)? If yes, go back to a FIFO design.
2. ~~How does settlement consume decisions?~~ **Decided:** a monthly CSV report, emailed through SES (see "Monthly settlement report" below). Settlement has no AWS access. Still to confirm with settlement: the mailbox, the day cut-off (UTC or local), the columns, and whether their security policy allows financial data in email attachments.

## Option A: SQS standard queue, one Lambda, DynamoDB

**Summary:** A standard queue feeds one decision Lambda, and every decision is written to a DynamoDB table that the settlement team reads.

**Services in order:** Passenger API → SQS standard queue → Lambda → DynamoDB decisions table. A DLQ is attached to the queue.

| Hop | 1 Push/pull | 2 Sync/async | 3 Payload | 4 Role | 5 Failure | 6 Corr. ID |
|---|---|---|---|---|---|---|
| Passenger API → SQS | Push (`SendMessage` from the API backend) | The passenger waits only until SQS accepts the message, then gets `202 Accepted`. The decision comes later. | Cancellation JSON v1 plus `event_id` (generated by the API or taken from a client idempotency key). The API owns the schema, additive changes only. | API backend role: `sqs:SendMessage` on the one queue ARN | The API returns 5xx and the client retries with the same key. Standard queues do no dedup, so duplicates are possible and the Lambda handles them. | `X-Correlation-Id` header or minted, set as the `correlation_id` message attribute |
| SQS → Lambda | Pull (event source mapping polls) | Async to the API, batch runs synchronously | SQS event, `body` is a JSON string | Lambda role: `sqs:ReceiveMessage`, `DeleteMessage`, `GetQueueAttributes` on the queue | `ReportBatchItemFailures` on: only failed messages are retried, up to `maxReceiveCount`, then DLQ. One bad message never blocks others. | Read from the message attribute, minted if missing |
| Lambda → DynamoDB | Push (`PutItem`) | Sync, SDK timeout of a few seconds | Item: `pnr`, `event_id`, `decision`, `refund_rule_id`, `refund_amount` (string), `ts`, `correlation_id` | Lambda role: `dynamodb:PutItem` on the table ARN, conditional write on `event_id` | Throttle or timeout fails the record, SQS redelivers, and the conditional write makes that idempotent | Stored on the item and on every log line |

**Risks:**
1. At-least-once delivery means duplicates and out-of-order processing. If a cancel-then-reinstate case exists, a standard queue can apply them in the wrong order.
2. The only duplicate guard is the conditional write on `event_id`. If the producer ever sends two different `event_id`s for the same cancellation, both get a decision.

**Cost driver:** Request volume (about 60k messages a month) and DynamoDB on-demand writes, doubled by the report index. Both are close to zero at this scale.

**Settings to keep messages from waiting:**
- `BatchSize=1` or a small batch, no batching window, short function timeout (about 10 s).
- Visibility timeout at least 6 times the function timeout, `maxReceiveCount` about 3.
- Do not set reserved concurrency too low. A standard queue lets Lambda scale to many parallel invocations.

**DynamoDB:** The system of record for decisions. Partition key `pnr`, sort key `event_id`, so settlement can query all decisions for a booking. The key is for lookups, not ordering. On-demand capacity, point-in-time recovery on. Do not store passenger name or email.

**Handler fit:** The existing handler already matches this option. It returns only the failed `messageId`s. It still needs the conditional DynamoDB write, which the lab version deliberately leaves out.

## Option B: SNS standard fan-out to decision and settlement queues

**Summary:** An SNS topic delivers each event to a decision queue and a separate settlement-audit queue.

**Services in order:** Passenger API → SNS topic → two SQS standard queues (decision, audit). The decision queue feeds the decision Lambda → DynamoDB. The audit queue feeds an audit Lambda → S3 (a private bucket).

| Hop | 1 Push/pull | 2 Sync/async | 3 Payload | 4 Role | 5 Failure | 6 Corr. ID |
|---|---|---|---|---|---|---|
| Passenger API → SNS | Push (`Publish`) | Sync call, async delivery, API returns 202 | Cancellation JSON v1 plus `event_id`, additive changes only | `sns:Publish` on the topic ARN | The API retries with the same `event_id` | Message attribute `correlation_id` |
| SNS → SQS (×2) | Push | Async | SNS envelope, raw message delivery on | Queue policy allows `sns.amazonaws.com` to send, conditioned on the topic ARN | SNS retries delivery, an SNS DLQ is attached | The attribute is forwarded |
| SQS → decision Lambda | Pull | Batch runs synchronously | SQS event | `ReceiveMessage`, `DeleteMessage` on the decision queue | Partial batch failure, retry, then DLQ | Read or mint |
| Decision Lambda → DynamoDB | Push | Sync | Decision item | `PutItem` on the table | Conditional write makes retries idempotent | Item attribute |
| SQS → audit Lambda → S3 | Pull, then push | Sync | Decision record as JSON lines | `s3:PutObject` on `audit/*` only | Retry, then audit DLQ | Object metadata `x-amz-meta-correlation-id` |

**Risks:**
1. Four to five hops and about six components make operations and debugging heavier than A.
2. Two queues can drift apart, so the audit trail needs a reconciliation check against the decisions table.

**Cost driver:** SNS plus a second queue per message, and S3 PUT requests. Still small at 60k messages a month.

## Option C: EventBridge bus with rules

**Summary:** The API publishes each cancellation to an EventBridge bus, a rule routes it to the decision queue, and the decision Lambda publishes each decision back to the bus so settlement can subscribe.

**Services in order:** Passenger API → EventBridge custom bus → rule → SQS standard queue (with DLQ) → decision Lambda → DynamoDB decisions table → EventBridge (decision event) → settlement targets.

| Hop | 1 Push/pull | 2 Sync/async | 3 Payload | 4 Role | 5 Failure | 6 Corr. ID |
|---|---|---|---|---|---|---|
| Passenger API → EventBridge | Push (`PutEvents`) | Sync call, async delivery, API returns 202 | Event with detail type `cancellation.received`, versioned in `detail`, additive changes only | `events:PutEvents` on the bus ARN | `PutEvents` can partially fail, so check `FailedEntryCount` and retry | Event `detail.correlation_id` |
| EventBridge → SQS | Push (rule target) | Async | The event, `detail` holds the cancellation JSON | The queue policy allows `events.amazonaws.com` to send, conditioned on the rule ARN | The rule target has retries and a DLQ | Kept in `detail` |
| SQS → decision Lambda | Pull | Batch runs synchronously | SQS event wrapping the EventBridge event | `ReceiveMessage`, `DeleteMessage` on the queue | Partial batch failure, retry, then DLQ | Read from `detail`, minted if missing |
| Decision Lambda → DynamoDB | Push | Sync | Decision item | `PutItem` on the table, conditional on `event_id` | Conditional write is idempotent | Item attribute |
| Decision Lambda → EventBridge | Push (`PutEvents`) | Sync | Event with detail type `cancellation.decided`, versioned in `detail` | `events:PutEvents` on the bus ARN | Check `FailedEntryCount` and retry, a failure fails the record and SQS redelivers | Event `detail` field |

**Risks:**
1. EventBridge adds a routing layer that this volume doesn't need, and rules, event patterns and targets are another thing to debug.
2. Publishing the decision after the table write is two separate steps. If the second fails after the first succeeds, settlement can miss an event unless the retry republishes it, so the publish must also be idempotent.

**Cost driver:** EventBridge events (two per cancellation) plus queue and DynamoDB requests. Small at this volume, but the highest of the three.

## Monthly settlement report (applies to A, B and C)

Settlement has no AWS access, so the decisions table is turned into a CSV and emailed.

**Flow:** EventBridge Scheduler (monthly) → report Lambda → DynamoDB date index → zipped CSV in a private S3 bucket → SES email to a shared settlement mailbox.

- **Index:** Add a global secondary index on the decisions table with partition key `decision_date` (`YYYY-MM-DD`) and sort key `ts`. Project only the columns the CSV needs. No scans.
- **Query:** Query the index once per day of the month (28 to 31 queries) and paginate each with `LastEvaluatedKey`. A single `Query` call returns only the first 1 MB.
- **Size:** About 60k rows is roughly 18 MB in DynamoDB and a 10 to 15 MB CSV. Zip it before emailing (about 2 MB), well under mailbox limits.
- **Columns:** `pnr`, `ticket_number`, `airline_code`, `event_id`, `fare_class`, `decision`, `refund_rule_id`, `refund_amount`, `ts`. No passenger name or email.
- **Idempotent output:** The key is `reports/month=YYYY-MM/decisions.zip`, so a re-run overwrites rather than duplicates. Log `record_count` and compare it with the events accepted that month.
- **Lambda sizing:** 512 MB to 1 GB memory, 2 to 5 minute timeout.
- **Cost:** The month's queries cost well under a cent. The index roughly doubles write cost, still a few cents a month. Prices were not verified live (the pricing API was blocked), so check them before quoting.
- **Not needed at this volume:** Athena, QuickSight, SFTP or a download portal.

| Hop | 1 Push/pull | 2 Sync/async | 3 Payload | 4 Role | 5 Failure | 6 Corr. ID |
|---|---|---|---|---|---|---|
| Scheduler → report Lambda | Push | Async | Scheduler event with the report month | Scheduler role: `lambda:InvokeFunction` on the function | Scheduler retries, then DLQ | Minted per run, on every log line |
| Report Lambda → DynamoDB | Pull (`Query` on the index) | Sync | Items for one `decision_date` | `dynamodb:Query` on the table and index ARNs | Retry, then fail the run and alert | Same run ID |
| Report Lambda → S3 | Push (`PutObject`) | Sync | Zipped CSV | `s3:PutObject` on `reports/*` | The same key makes a re-run safe | Object metadata `x-amz-meta-correlation-id` |
| Report Lambda → SES | Push (`SendRawEmail`) | Sync | Email with the zip attached | `ses:SendRawEmail` on the verified identity ARN only | Retry, then alert. A missed report must not fail silently. | Run ID in a custom header, never in the body |

**SES setup:**
- Verify the sender identity (domain or address). In an SES sandbox, also verify each recipient.
- Send to a shared settlement mailbox, not individuals. Keep the address in an environment variable, not in code.
- Log only counts and the report month, never recipients or file contents.
- If the file ever outgrows email (a yearly report is about 150 MB), send monthly files or use a CloudFront signed link instead.

## Failure handling and alerts (applies to A, B and C)

**Failed cancellation events**
- **Retry:** With `ReportBatchItemFailures` on, SQS redelivers only the failed message, up to `maxReceiveCount` (about 3).
- **DLQ:** After the last attempt the message moves to a dead-letter queue (a standard queue). Set its retention to the 14-day maximum, which is longer than the source queue's. In B, both queues need a DLQ. In C, the rule target also gets its own DLQ.
- **Alert:** A CloudWatch alarm on the DLQ's `ApproximateNumberOfMessagesVisible > 0` publishes to an SNS topic, whose email subscription notifies a shared team mailbox.
- **Replay:** After the cause is fixed, use SQS DLQ redrive to move the messages back to the source queue. This is safe because the conditional write on `event_id` makes a repeat harmless.

**Failed monthly report**
- **Retry:** The scheduler invokes the report Lambda asynchronously, so Lambda retries a failed run twice by default.
- **After retries:** An on-failure destination (an SQS queue or the same SNS topic) captures the failed event.
- **Alert:** A CloudWatch alarm on the function's `Errors` metric also publishes to the SNS topic.
- **Replay:** Re-run the Lambda for that month. The same S3 key makes this safe.

| Hop | 1 Push/pull | 2 Sync/async | 3 Payload | 4 Role | 5 Failure | 6 Corr. ID |
|---|---|---|---|---|---|---|
| Queue → DLQ | Push (redrive policy) | Async | The original message, unchanged | The queue's redrive policy names the DLQ ARN | Held for up to 14 days | The `correlation_id` attribute travels with the message |
| DLQ alarm → SNS | Push | Async | Alarm state notification (alarm name and metric, no event data) | The alarm action targets the topic ARN | The alarm keeps firing until the queue is empty | Not applicable, so name the queue in the alarm text |
| SNS → email | Push | Async | Alarm text | The topic policy allows CloudWatch to publish | An unconfirmed or bounced subscription drops alerts, so test it | Not applicable |
| Report Lambda → on-failure destination | Push | Async | The failed invocation record | Lambda role: `sqs:SendMessage` or `sns:Publish` on that one ARN | Held until someone re-runs the report | Run ID in the record |
| DLQ → source queue (replay) | Push (move task, started by a person) | Async | The original messages | The operator needs `sqs:StartMessageMoveTask` and related actions on both ARNs | Fix the cause first, or they return to the DLQ | Preserved |

**Cautions**
- **The DLQ holds the full payload, including passenger name and email.** Limit read access to named people, keep encryption on, and never copy message bodies into tickets, chat or logs.
- **Email subscriptions need a click to confirm.** Someone on the team must accept it, or alerts silently go nowhere. Send to a shared mailbox, not an individual. Keep the address in an environment variable.
- **Alarm text:** Alarms carry only the alarm name and metric, never event data.
- **Cost:** The DLQ is about $0. SNS email is free for the first 1,000 notifications a month. Alarms are about $0.10 each, so roughly $0.20 to $0.30 a month for the DLQ and report alarms. Prices were not verified live, so check them before quoting.

## Logging with CloudWatch Logs (applies to A, B and C)

Every application line follows `docs/LOGGING_CONTRACT.md`: one JSON object of at most 2 KB, with `ts`, `level`, `service`, `correlation_id`, `boundary` and `message`, plus only the allowed identifier and count keys. Never log the body, passenger name, email or fare amount, and no raw exception messages.

- **Log groups:** One per Lambda (decision, report, and in B the audit Lambda), created in SAM with the `accelya-m2-<learner>-` naming.
- **Retention:** Set it in SAM (30 days is a sensible start). By default logs never expire.
- **Levels:** `DEBUG` stays off in deployed functions. Failures log at `ERROR` with a non-empty `error_type`. A decision sent to manual review logs at `WARNING`.
- **Volume:** With `BatchSize=1`, each message writes 4 application lines (`batch.received`, `cancellation.received`, `cancellation.decided`, `batch.completed`) of about 300 to 350 bytes, plus the 3 Lambda platform lines (`START`, `END`, `REPORT`). That is about 1.8 KB per message, so about 110 MB a month at 60k messages.
- **Tracing:** Every line carries `correlation_id`, and per-record lines carry `message_id`, so one Logs Insights query follows a cancellation end to end.
- **Alerts:** The alarms from the failure-handling section cover the DLQ and the report. An optional metric filter on `ERROR` lines costs about $0.30 a month as a custom metric.
- **Encryption:** The default is free. A customer-managed KMS key on a log group adds about $1 a month per key.
- **Checking:** Validate output with `python3 day2/scripts/check_logs.py` against the contract.
- **Option for trimming:** The two `batch.*` lines repeat information when the batch size is 1. Dropping them would cut volume by about a third, but the saving is a fraction of a cent.

| Log hop | 1 Push/pull | 2 Sync/async | 3 Payload | 4 Role | 5 Failure | 6 Corr. ID |
|---|---|---|---|---|---|---|
| Lambda → CloudWatch Logs | Push (the runtime writes stdout) | Async | One JSON line per event, contract shape | Execution role: `logs:CreateLogStream` and `logs:PutLogEvents` on that function's log group ARN | A lost line is not retried, so keep lines small and avoid depending on logs for correctness | On every line |

**Estimated monthly cost** (rough, at 60k decisions a month, prices not verified live)

| Item | Monthly cost |
|---|---|
| SQS, decision Lambda, report Lambda, EventBridge Scheduler, SES | about $0 (inside free tiers) |
| DynamoDB (writes, report index, point-in-time recovery) | about $0.10 |
| S3 (zipped monthly report) | under $0.01 |
| CloudWatch Logs (about 0.11 GB ingested, 30-day retention) | about $0.05 to $0.10, probably inside the 5 GB free tier |
| CloudWatch alarms and SNS | about $0.20 to $0.30 |
| **Total for Option A with report, DLQ and logging** | **about $0.45 to $0.55** |

Option B adds roughly $0.05 to $0.10 and C roughly $0.15 or more. Not included: the existing passenger API, data transfer, support plans, and any customer-managed KMS key. Check current prices before quoting these figures.

## Comparison

| | A: SQS standard | B: SNS fan-out | C: EventBridge |
|---|---|---|---|
| Ordering | None (not required) | None | None |
| Duplicate handling | Conditional write on `event_id` | Same | Same |
| Components | 3 (plus 4 for the report) | 6 (plus 4) | 7 (plus 4) |
| Settlement visibility | Monthly emailed CSV | Monthly emailed CSV plus audit bucket | Monthly emailed CSV plus decision events |
| Biggest failure mode | Duplicates or reordering if the assumption is wrong | Queue drift | A decision saved but not published |
| Fits non-goals | Yes | Yes | Yes |
| Relative cost | Lowest | Low | Low to medium |
| Complexity | Low | Medium | High |

**Recommendation:** Option A. Without an ordering requirement, a standard queue is the simplest design that does the job, and the existing handler already fits it. Choose C only if settlement needs each decision pushed to it. Choose B only if settlement needs its own independent copy of every decision. Before building, confirm with the business owner that no case depends on event order, and add the conditional DynamoDB write to the handler.
